# This is NOT the Next.js you know

This version has breaking changes — APIs, conventions, and file structure may all differ from your training data. Read the relevant guide in `node_modules/next/dist/docs/` before writing any code. Heed deprecation notices.

Known Next 16 gotchas already honored in this codebase: `params`/`searchParams` are Promises (await them), `error.tsx` receives `unstable_retry` not `reset`, no `export const dynamic`/`revalidate` (data loaders call `connection()` instead), nav hooks come from `next/navigation`.

# Project conventions

## Architecture (don't fight it)

- **Hybrid storage.** Reference data (muscles, modalities, equipment) is TypeScript in `src/lib/data/` with id unions — never move it to the DB. Mutable data (clients, exercises + their muscle scores/modality variants, routines, programs, program_days, assignments, sessions, set_logs, weigh_ins) is Supabase; schema lives in `supabase/schema.sql` (run by hand in the SQL editor — the publishable key can't DDL); changes to an existing DB ship as idempotent files in `supabase/migrations/`, and code must tolerate a not-yet-migrated DB on reads. Clients live in the DB (so people can be added/edited at `/users`): `ClientId` is an open string, the TS roster in `src/lib/data/clients.ts` is seed + read-only fallback (`GymData.clientsSource === "seed"` while the clients table doesn't exist), and client ids are validated at write time via `assertClientId` in `src/lib/db/guards.ts` (server-only, deliberately not a `"use server"` file — every export there is a public endpoint), not a compile-time union. Client card colors come from the `CLIENT_COLORS` presets only — never free hex (a person's existing off-preset color survives a re-save; changing the presets means migrating rows). Exercises follow the same pattern (authored at `/exercises`): `ExerciseId` is an open string, `src/lib/data/exercises.ts` is seed + read-only fallback (`GymData.exercisesSource === "seed"`; the three catalog tables fall back as a unit), ids are validated at write time via `assertExerciseIds` in `src/lib/db/guards.ts`, and the DB is seeded via the Import button at `/exercises`, never SQL inserts. The catalog reaches client components only as the serializable `ExerciseCatalog` slice (plain arrays via `catalogSlice`; lookups rebuilt with the WeakMap-cached `exerciseLookup` in `src/lib/exercise-catalog.ts`) — never pass full `GymData` or Maps across the boundary. Muscle scores are authored as roles (`SCORE_ROLES`: primary 10 / secondary 7 / supporting 4 / stabilizer 2, ≤2 primaries, ≤9 muscles — enforced in `saveExercise`) so hand-added exercises can't inflate the heat map; seed rows keep hand-tuned values.
- **Reads = snapshot.** Server pages call `loadGymData()` (`src/lib/db/snapshot.ts`, server-only, per-request `cache()`); it falls back to the TS seed (`GymData.source === "seed"`) only while the migration hasn't run. Query functions in `queries.ts`/`modality.ts`/`coverage.ts` are pure and synchronous over `(data: GymData, ...)` — keep new ones that way; never fetch inside them.
- **Writes = server actions** in `src/lib/actions/`. The browser never imports the Supabase client. Every action validates text FKs against the unions via `src/lib/validate.ts` (exercise ids against the live table via `assertExerciseIds`) and ends with `revalidateAll()` (`revalidatePath("/", "layout")`). Form/payload parsing and validation rules are pure functions in `validate.ts` with tests — actions stay thin. Missing-table checks go through `isMissingTable` (`src/lib/db/guards.ts`). A `"use server"` file exports only async actions — no types (Next's action compiler fails the build on `export type {…}`) and no helpers (every export is a public endpoint); payload types live in `validate.ts`. A write that touches several rows/tables at once must be all-or-nothing: make it a Postgres function (in `schema.sql` AND a migration) and call it through `rpc()` in `_helpers.ts`, registering the function's migration in `RPC_MIGRATION` so an un-migrated DB gets a "run file X" error. Integrity the app relies on (client FKs, unique set positions, one active assignment) is enforced in the DB too — don't remove the app-side checks, they give the readable messages.
- **snake_case rows ↔ camelCase types** map only in `src/lib/db/mappers.ts`. `RoutineExercise.order` ↔ column `sort_order`; both mapper directions must stay complete when a type changes.

## Domain invariants (the model's whole point)

- Loads are honest: `LoadPrecision` is `exact`/`approximate`/`ordinal`. Ordinal (hip-band) work NEVER gets a pound value, an e1RM, or a place in a lbs total — it's tracked as band rank + reps and shown as band + reps text, never as a bar or number in pounds.
- Conditioning (Echo Bike) is pattern `conditioning` + modality `cardio`: one SetLog per piece with its target and console readout in `SetLog.conditioning` (`RoutineExercise.conditioning` holds the row's default target). No muscle scores, no pounds, no e1RM — gate any strength math with `isStrengthPattern` (`src/lib/exercise-catalog.ts`), which also excludes mobility. Targets, schemes and labels live in `src/lib/conditioning.ts`; a person's target rolls forward from their last piece (`conditioningTarget`). A dumbbell/barbell/ankle-weight set LOGged at 0 lb becomes bodyweight (`completeAsBodyweight` in `src/lib/set-blocks.ts`). Ankle weights (`ankle_weight` modality, `ankleWeights` inventory) are exact pounds per ankle but never get an e1RM or a cross-modality transfer — they progress by reps.
- `SetLog.reps` is per side; `weightLbs` is per implement; totals are derived (`setLoad`).
- `SetLog.position` is session-wide performed order and must survive every structural edit — `blocksFor`/`toBlocks` group consecutive sets by it. Renumber via `renumber()` in `src/lib/set-blocks.ts`.
- Muscle work derives from `exerciseMuscleScores` × modality modifiers (`effectiveScores`); exercises deliberately have no muscleGroup field. A modality modifier adjusts, never introduces, a muscle.
- Ids are readable slugs (`newId`/`slugId` in `src/lib/ids.ts`), never numbers.
- Date/time helpers live ONLY in `src/lib/periods.ts` (local ISO strings for display/storage, UTC day numbers for trend math — never mix). Meter view-model types live in `src/lib/meters.ts`; session card label/cursor helpers in `src/lib/session-labels.ts`. New-row defaults (routine prescription, fresh session sets) live in `src/lib/set-templates.ts`; the home launcher's rows and its plan-value contract with `startGroupFromForm` in `src/lib/launcher.ts` (build/read values only via `planValue`/`parsePlanValue`); live-session props for the runner and board in `livePerson` (`src/lib/live-session.ts`).

## UI conventions

- Tailwind v4 utilities only, no component library. Color comes from semantic tokens in `globals.css` (`@theme inline`): surfaces (`background`/`surface`/`surface-input`), borders (`border`/`border-strong`), text (`foreground`/`muted`), the blue accent family (`accent`/`accent-strong`/`accent-fg`/`accent-text`/`accent-soft`), the warm amber-orange action family (`accent-warm`/…, filled primary "do the thing" buttons only — deliberately more orange than the gold `warning` token), and reserved status colors `success`/`warning`/`danger` (+ `-text` variants, `danger-fg` for ink on a filled danger badge) meaning good/okay/bad; `scrim` is the modal backdrop, `shadow` the elevation color; muscle-group identity hues are `--group-*` (read via `MUSCLE_GROUP_COLORS`, which holds `var()`s). Never hardcode a hex in a component. `currentColor` blends (`hover:bg-current/5`, `bg-current/10` chips) survive only as hover washes and neutral tags. Mono for numbers.
- **Status color is never the only encoding** — pair it with a text label and legend (`StatusLabel`/`MeterLegend` in `src/components/meter-rows.tsx`); red↔green alone is colorblind-hostile. Ordinal (hip-band) work never renders as length in a lbs bar.
- Controls come from `src/components/ui.tsx` (`Button`/`Input`/`NumberInput`/`Select`/`Field`/`IconButton`/`Card`/`PageShell`/`ChipTabs`); modal overlays (picker, Explain sheet, side sheets) go through `Dialog` (`src/components/dialog.tsx` — portal, scrim, Escape, dialog semantics): inputs sit on `bg-surface-input` at `text-base` (16px — anything smaller makes iOS Safari zoom on focus), touch targets are ≥44px (`min-h-11`/`size-11`; `size="sm"` is 36px for dense mouse layouts and grows to 44px under `pointer-coarse:` — hand-rolled small controls must do the same), focus is `focus-visible:ring-2 ring-accent/60` — never bare `outline-none`. Pages wrap in `PageShell`; wide tables get the `-mx-4 overflow-x-auto px-4 sm:mx-0 sm:px-0` scroller.
- Mobile-first: nav is a top bar on `md:+` and a fixed bottom tab bar below (`PageShell`'s `pb-24` clears it). Dark mode is media-query driven (`color-scheme: light dark` set on `:root`). The heat ramp (`--heat-0..12`) is a graded status scale — danger → warning → success, OKLab-interpolated from the status tokens, with its own dark-mode anchors (hue carries meaning, so no reversal) — and stays out of `@theme`; zero work renders outline-only, never the red end.
- Server components by default; interactivity lives in `'use client'` files under `src/components/`. Session editing goes through the `useSetEditor` hook (debounced `updateSetLog` for field edits, `syncSetLogs` for structural changes) — the solo runner and group-board cards both use it, plus `useSessionActions` (picker, add/swap, "continue your workout?"). Server actions called from handlers go through `runAction` (`src/components/run-action.ts`) so redirect signals pass through; FormResult forms use `useFormAction`.
- The body figure (`BodyFigure`, shared by the coverage heat map, "Explain exercise" and Library › Muscles) draws regions from `src/lib/body-map.ts`, a `Record<MuscleId, …>` so an unmapped muscle is a compile error; one view (front or back) per muscle. Regions are clipped to the silhouette and `body-map.test.ts` keeps them inside it and non-overlapping. The heat map shows prescribed coverage only; Explain shades by role and the explorer by muscle group.

## Verify before done

`npm run verify` (typecheck + lint + unit tests + build; the pure query layer is tested with vitest against `seedSnapshot()` — add tests beside the module as `src/lib/*.test.ts` when touching domain math), then render-check touched routes against the dev server (usually already running on :3000 — don't kill it, don't start a second one on the same project). Write-path changes need the live DB (schema.sql applied). For SVG/visual work: extract the SSR'd markup, rasterize with `qlmanage -t`, and actually look at it.
